## 5. The class registry and the hierarchy (`.data`)

The `CRPG_*` class registry is a table of records `{ char* name; void* factory;
record* parent; ... }` in `.data` around 0x1082d838..0x1082dda0. Decoded (word 0 of
each record is the class-name pointer, word 1 the factory, word 2 the parent record):

    class                        factory     parent
    CRPG_Object                  0x1026f240  CReferenceCount
    CRPG_Object_Item             0x10265d90  CRPG_Object
    CRPG_Object_Collectible      0x10265e00  CRPG_Object_Item
    CRPG_Object_Inventory        0x10269210  CRPG_Object
    CRPG_Object_AngelusChain     0x10269740  CRPG_Object_Weapon
    CRPG_Object_Gun              0x10269aa0  CRPG_Object_Weapon
    CRPG_Object_Melee            0x1026b9a0  CRPG_Object_Item
    CRPG_Object_Ulaks            0x1026ba10  CRPG_Object_Melee
    CRPG_Object_RocketMelee      0x1026ba80  CRPG_Object_Summon
    CRPG_Object_CreatureAttack   0x1026d4f0  CRPG_Object_Item
    CRPG_Object_Char             0x10273150  CRPG_Object
    CRPG_Object_Ammo             0x102741f0  CRPG_Object_Item

`CRPG_Object_Collectible` sits between `CRPG_Object_Item` and its own subclasses;
`CRPG_Object_Inventory` is a *sibling* branch off `CRPG_Object`, not the owner of the
`VIEWMODEL` slot. The .rdata proximity ADR-0492 relied on (`"VIEWMODEL" 0x1075a144`,
`"CRPG_Object_Inventory" 0x1075a16c`) is string-pooling order, not class membership.

## 6. Which classes own the loader, and where the `VIEWMODEL` override sits

An image-wide scan for the 4-byte value of each address, resolved to the vtable that
holds it (walk back to the preceding RTTI pointer) and its RTTI name:

    FUN_10260940 (the loader)     0x107572fc -> vtable 0x107572dc slot  8  CRPG_Object_Item
    FUN_10260940 (the loader)     0x1075aa2c -> vtable 0x1075aa0c slot  8  CRPG_Object_CreatureAttack
    FUN_10260940 (the loader)     0x1078959c -> vtable 0x1078957c slot  8  CRPG_Object_Telephone_Receiver
    FUN_10265a70 (VIEWMODEL)      0x10759ed4 -> vtable 0x10759eb4 slot  8  CRPG_Object_Collectible
    FUN_10265ab0 (ATTACH*)        0x10759ee4 -> vtable 0x10759eb4 slot 12  CRPG_Object_Collectible

Slot 8 is the item's **model-load virtual**. The base implementation is
`FUN_10260940` (Item / CreatureAttack / Telephone_Receiver); `CRPG_Object_Collectible`
**overrides** it with `FUN_10265a70`, which calls the base loader and then *also* reads
`VIEWMODEL`. No vtable of any weapon class (`Gun`, `Melee`, `Ulaks`, `AngelusChain`, ...)
holds either function, and the `VIEWMODEL` literal has no other code xref, so the
`VIEWMODEL` property is read only by the collectible class's own model-load override.

## 7. What this resolves (GH #67 step 1) and what it does not

Resolved:

- **read, not set:** the `VIEWMODEL` literal is a *definition key read* at
  model-load time (`FindChild(name)` -> child value -> object property slot 0x68;
  sec 2/3). ADR-0492's "read-vs-set not resolved" is closed on the READ side.
- **the owner:** `CRPG_Object_Collectible` slot 8 (RTTI-verified, sec 4) -- ADR-0492's
  `CRPG_Object_Inventory` attribution is corrected (sec 5).
- **the consumer path:** it is the item *model* pipeline (`FUN_10260940`'s key list,
  sec 3): the engine names item models by definition keys, including a `VIEWMODEL`
  override on the collectible class.

Not resolved / honest limits:

- **It is NOT established that the player's first-person arms are this property.**
  No weapon class reads `VIEWMODEL`; the property is read only by the *collectible*
  class's model-load override. (That a collectible is the item you pick up / inspect is
  an inference from the class name and the class list in sec 5, not a measurement.)
  ADR-0492's consequence "the arms reach GL as an already-transformed, item-owned model"
  is therefore weakened: the only item-owned model reference the engine reads under this
  name belongs to the collectible class.
- The object-side member that receives the value (destination vtable slot 0x68) is not
  traced to a `CXR_ModelInstance` creation; that consumer is still not located.
- The roles of `FUN_1026d790`'s two object parameters (registry vs destination) are as
  Ghidra rendered them and are not fully disambiguated; the direction claim rests on
  the *usage pattern* in `FUN_10260940` (a loader that fills an object from a
