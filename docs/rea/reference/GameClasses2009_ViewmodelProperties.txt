## 1. Reproducer (read-only)

    import struct, hashlib
    p = r"F:\The Chronicles of Riddick - Assault on Dark Athena\Content\GameClasses_Win32_x86.dll"
    d = open(p, "rb").read()
    print(hashlib.sha256(d).hexdigest())        # d7e81d7d… (above)

    def cstr(va):                                # VA == 0x10000000 + fileoff here
        o = va - 0x10000000
        return d[o:d.find(b"\0", o)].decode("latin1")

    def refs(va):                                # imm32 cross-references (raw)
        pat = struct.pack("<I", va); out=[]; s=0
        while True:
            i = d.find(pat, s)
            if i < 0: return out
            out.append(0x10000000+i); s = i+1

    # the RPG item flag-name table (bit-ordered) starts at VA 0x1082d728
    for bit in range(32):
        print(bit, cstr(struct.unpack_from("<I", d, 0x82d728+4*bit)[0]))
    for name, va in (("VIEWMODEL",0x1075a144),("ATTACHPOINT",0x1075a150),
                     ("ATTACHROTTRACK",0x1075a15c),("CRPG_Object_Inventory",0x1075a16c)):
        print(name, hex(va), [hex(r) for r in refs(va)])

the 2004 module's mask scan (docs/rea/reference/GameClasses_NoviewmodelRuntime.txt).

## 3. `VIEWMODEL` / `ATTACHPOINT` / `ATTACHROTTRACK` are item-class property names

At VA 0x1075a144 the `.rdata` string block is:

    0x1075a144  "VIEWMODEL\0"
    0x1075a150  "ATTACHPOINT\0"
    0x1075a15c  "ATTACHROTTRACK\0"
    0x1075a16c  "CRPG_Object_Inventory\0"
                0x1075a182  "Force Equipping item - Ident: %d"   (0x1075a208)

Each of the three property names has **exactly one** cross-reference, and all
three are in the **same code neighbourhood** (file `0x265a92`..`0x265b9d`,
VA `0x10265a92`..`0x10265b9d`):

| property string | VA | sole code xref (VA) | containing function |
|---|---|---|---|
| `VIEWMODEL` | 0x1075a144 | 0x10265a92 | `FUN_10265a70` (leaf, `ret 0Ch`) |
| `ATTACHROTTRACK` | 0x1075a15c | 0x10265b7a | `FUN_10265ab0` |
| `ATTACHPOINT` | 0x1075a150 | 0x10265b9d | `FUN_10265ab0` |

`CRPG_Object_Inventory` (the class-name string) is referenced once, from `.data`
VA 0x1082d9ec (a class-registry table). So the three names are declared next to the
`CRPG_Object_Inventory` class name and each is *used* from code.

### 3a. `FUN_10265ab0` reads `ATTACHROTTRACK`/`ATTACHPOINT` as bool properties

Disassembly (from the raw bytes; the function's SEH prologue is at VA 0x10265ab0):

    10265b7e  8b ce              mov  ecx,esi           ; this

    10265b85  85 c0              test eax,eax
    10265b87  5f                 pop  edi

### 3b. `FUN_10265a70` references `VIEWMODEL`

> `call 0x100162e0` below is the **`CStr` string constructor** (a temporary built

> lookup — `0x100162e0` = `CStr::CStr(const char*)`, which installs
> `CStr::vftable` and calls vtable slot `0x68`. The literal is passed by name into
> `FUN_1026d790`. Read-vs-set is still unresolved (its callees/callers are not
> decompiled).

    10265a70  8b 44 24 0c        mov  eax,[esp+0Ch]
    ...

## 4. `FirstPerson` / `ThirdPerson` are adjacent entries in a view-mode name table

VA 0x1083ff68 -> `0x1078be28` `"FirstPerson"`; VA 0x1083ff6c -> `0x1078be1c`
`"ThirdPerson"` (adjacent dwords, in a `.data` table whose neighbours are code
pointers). The strings sit in `.rdata` next to `CWObject_InputEntity`
(0x1078be04) and, further on, `CWObject_Matinee` / `.\WObj_Misc\WObj_Matinee.cpp`.
This reads as a **view-mode / camera-mode name list** for an entity. Class identity
is not proven (§ "not claimed").

## 5. The 2009 module does not fit the provider's analysis budget

> **CORRECTED (wake 92 / ADR-0493).** This is the *default* 330 s deadline, not a
> limit of the module. With `REA_GHIDRA_STARTUP_TIMEOUT_MS=1500000` the same
> requests return **exit 0** (382 s / 380 s wall; see
> `GameClasses2009_ViewmodelDecompiled.txt`). Also measured there: `--snapshot`
> does **not** reduce the per-call cost (the second call re-imported and
> re-analysed). The `provider_timeout` record below is kept as the *record of the
> default budget*; the "repeating the unchanged request is not expected to

The full-function analysis that would decompile `FUN_10265a70`/`FUN_10265ab0`

Both are the same 330 s analysis budget being exceeded on the 9.0 MB module (the

`rea doctor` reports Ghidra 12.1.4 healthy, and the deep-REA corpus in this
directory (`MXR_*`, `MCCDyn_*`, `GameClasses_NoviewmodelRuntime`) is all the
**2004** build — `GameClasses_Win32_x86.dll` there is 2,219,520 B; the 2009 module

`RndrGL_Input_Path.txt` is the 2009 module), so the budget is a size/analysis-limit,
not a broken installation. Consequence: the 2009 engine-side code path needs either
a persistent analysis snapshot across wakes or a smaller module; a single 330 s
request is not enough for this DLL.
